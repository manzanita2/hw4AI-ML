# project/m2/sim/

This directory holds the M2 deliverable artefacts that the grader checks
(per [`documents/hw4ai_ece510_project_milestone_2_spring26_r1.pdf`](../../documents/hw4ai_ece510_project_milestone_2_spring26_r1.pdf)
deliverable #2, checkboxes 4 and 5):

* `compute_core_run.log` -- plain-text simulation transcript with the
  compute_core testbench PASS lines. Regenerate with `make m2-log-compute_core`
  or the full `make m2-log` (which also refreshes `interface_run.log`) from
  `project/m2/tb/`.
* `interface_run.log` -- same for `tb_interface.py`; part of chained `make m2-log`.
* `waveform.png` -- annotated waveform PNG covering one full
  IDLE -> LOAD -> COMPUTE -> DRAIN tile. Regenerated manually; the
  procedure is below.

## Regenerating `compute_core_run.log`

```bash
cd project/m2/tb
make m2-log-compute_core   # clean + compute_core only -> copies log here
# or full M2 log bundle (compute + interface), see ../README.md:
make m2-log
```

The log will end with a line of the form

```
   462.00ns INFO     cocotb.compute_core                PASS: all 4 GEMM outputs matched bit-exact
```

which the grader greps for.

## Regenerating `waveform.png` (one-time manual step)

The committed save file [`project/m2/tb/compute_core.gtkw`](../tb/compute_core.gtkw)
pre-arranges all signals the M2 rubric asks for ("input application,
internal pipeline activity, and output capture, annotated"). Run:

```bash
cd project/m2/tb
make                            # produces artifacts/compute_core.vcd
gtkwave artifacts/compute_core.vcd compute_core.gtkw &
```

The save file lives in `tb/` and not `tb/artifacts/` on purpose, so
`make clean` does not delete it.

Inside gtkwave:

1. Press `Ctrl+Shift+F` (Zoom Fit) so the entire ~462 ns transcript fits
   on screen, OR set the time range to `0 ns .. 470 ns` manually.
2. Verify the four phases are visible side by side:
   - IDLE before `cfg_start`
   - LOAD: 16 cycles of `act_valid` + ramping `wt_count`
   - COMPUTE: `state == 2`, `compute_cycle` ramping 0 -> 9
   - DRAIN: `state == 3`, `res_valid`, `res_data` cycling through four bf16 outputs
3. `File -> Print` -> choose PDF, save to `compute_core_waveform.pdf` in this directory.
   (gtkwave does not export PNG directly; PDF is rubric-acceptable -- the PDF
   line states "PNG or PDF.")
4. If a PNG is preferred, convert with ImageMagick:
   ```bash
   convert -density 200 compute_core_waveform.pdf -quality 92 waveform.png
   rm compute_core_waveform.pdf
   ```

The screenshot does not need annotations beyond the signal names already
present in the gtkwave save file -- the rubric's "annotate signals" item
is satisfied by the `[FSM] / [Activation/Weight stream in] / [Result
stream out] / [Status]` group dividers shown in the gtkwave pane.

## What's NOT regenerated by `make m2-log`

* `waveform.png` (manual step above; gtkwave is interactive)
* `compute_core.vcd` (lives in `tb/artifacts/`, not committed; regenerate
  with any `make` invocation)
