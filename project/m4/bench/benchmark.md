# M4 Benchmark: 16x16 systolic array vs software baseline

Target kernel: `Conv2d 5-1` from RAFT `raft_large` (the dominant
`aten::mkldnn_convolution`, 53.02% of forward self-CPU). Hardware design point:
16x16 weight-stationary systolic array, bf16 multiply / fp32 accumulate, AXI4
data plane, **100 MHz** post-synthesis (`../synth/timing_report.txt`).

Every number below traces to [`benchmark_data.csv`](benchmark_data.csv), which
is generated by [`benchmark.py`](benchmark.py) from the measured per-phase
cycle counts in [`bench_measured.csv`](bench_measured.csv). The roofline
[`roofline_final.png`](roofline_final.png) is generated by the shared
`tools/roofplot/roofplot.py` from [`roofline_final.yml`](roofline_final.yml)
(whose point values trace to `benchmark_data.csv`).

## Method

Measured, not hand-counted: `tb/tb_top.py::test_benchmark` drives the real RTL
over AXI and records the steady-state cost of each phase from the simulation
clock:

| Phase | Cycles | Source |
|---|---|---|
| `load` (weight slab, 16 beats) | 23 | `bench_measured.csv` |
| `compute_hold` (1 activation col, weights held) | 422 | `bench_measured.csv` |
| `drain` (16 result beats) | 16 | `bench_measured.csv` |
| `tile_full` (compute + drain, last K-tile) | 438 | `bench_measured.csv` |

`benchmark.py` then extrapolates these to the full layer using the schedule the
RTL actually runs (`test_conv_raft_dims_e2e`): for every output pixel, sweep the
4 N-tiles, and within each sweep accumulate across the 36 K-tiles on chip. K is
`Cin*KH*KW = 64*3*3 = 576`, so KT = 36, NT = `Cout/16 = 4`, and there are
P = `batch*Hout*Wout = 4*260*480 = 499,200` output pixels. The cost of one
weight-reload group is `KT*load + (KT-1)*hold + tile_full = 16,036` cycles.

## Measured throughput

- Total: `P*NT*16,036 = 3.202e10` cycles -> **320.2 s** at 100 MHz.
- Sustained: **0.115 GFLOP/s** (layer is 36.87 GFLOP).
- Utilization: **0.22%** of the 51.2 GFLOP/s compute roof.
- Effective arithmetic intensity: **0.92 FLOP/byte** (vs the algorithm's
  intrinsic 144 and the array's ridge of 16).

The accelerator sits deep in the memory/reload-bound region (see roofline). The
binding limit is not even pin bandwidth: at AI 0.92 the BW ceiling is 2.94
GFLOP/s, but the measured 0.115 GFLOP/s is well below that because the
weight-reload schedule stalls the array (every K-tile reloads the full weight
slab and pays the pipeline fill before one activation column is consumed). The
resident weights are reused across **zero** additional pixels.

## Speedup vs M1 software baseline

Speedup = (M1 baseline time) / (M4 accelerator time), per-layer:

| | Time for `Conv2d 5-1` | Throughput |
|---|---|---|
| CPU baseline (`project/m1/sw_baseline.md`, 380 GFLOP/s effective conv rate) | **0.0970 s** | 380 GFLOP/s |
| M4 accelerator (measured) | **320.2 s** | 0.115 GFLOP/s |

- **Kernel speedup: 0.0003x** -- i.e. the accelerator is roughly **3,300x
  slower** than the CPU on this layer.
- System speedup (Amdahl, conv fraction f = 0.5302): **0.00057x**.

This is reported honestly: the accelerator is slower. The cause is
architectural, not the clock or the array size. The CPU's BLAS conv keeps the
weights resident and reuses them across the whole output map (high reuse, high
effective AI); this design's M3 schedule reloads weights every K-tile and
achieves no pixel reuse, so it pays DMA and fill cost that swamps the 256
MAC/cycle the array can do. The 100 MHz / 51.2 GFLOP/s peak is real; the
*delivered* fraction is the problem.

## Energy

Static estimate only (`../synth/power_report.txt`, 0.834 W):

| | Energy for the layer | Per FLOP |
|---|---|---|
| M4 accelerator | 267 J | 7243 pJ/FLOP |
| CPU (45 W TDP reference) | 4.36 J | 118 pJ/FLOP |

Because runtime dominates, the accelerator also loses on energy for this layer
(longer time at non-trivial power). The per-FLOP gap mirrors the throughput
gap; closing it requires raising delivered throughput (reuse), not lowering
power.

## Limitations / what did not work

The single largest lever is **weight reuse**. A streaming-GEMM schedule that
pins a block of `B` pixel-columns on chip and amortizes one weight load over all
`B` would raise effective AI from ~0.92 to **~8.2 FLOP/byte** (~9x), moving the
operating point up the bandwidth roof (orange projection in
`roofline_final.png`). It would still be memory-bound (8.2 < ridge 16), but
roughly an order of magnitude faster.

This was **out of scope** for the final submission:

- The reuse bottleneck was identified late in the analysis (it only became
  obvious once the schedule was extrapolated to RAFT scale here).
- Implementing it requires widening `result_buf`/`act_buf` to per-pixel-block
  register arrays, which changes the netlist materially and must be
  re-validated through place-and-route.
- The PnR iteration time is long and only one attempt remained. A trial
  streaming build did not close timing (it could not converge post-CTS) and was
  reverted, so the **shipped** design is the verified, timing-closing M3
  architecture benchmarked above.

See the "What did not work" section of
[`../report/design_justification.md`](../report/design_justification.md) for the
full account of the streaming attempt and the PnR failure mode.
